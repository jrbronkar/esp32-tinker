# MPU6050 IMU demo

This demo connects one MPU6050 breakout board to the ESP32-S3 DevKitC-1 over I²C. It confirms the sensor identity, wakes it from sleep, and streams acceleration, angular velocity, and temperature as both raw register values and physical units.

## Wiring

Disconnect the ESP32's USB cable before adding or changing wires.

| ESP32-S3 label | MPU6050 label | Purpose |
| --- | --- | --- |
| `3V3` | `VCC` | Supplies regulated 3.3 V power to the sensor |
| `GND` | `GND` | Gives both boards a common zero-volt reference |
| `8` (`GPIO8`) | `SDA` | Carries bidirectional I²C data |
| `9` (`GPIO9`) | `SCL` | Carries the I²C clock generated by the ESP32 |

The printed pin number is the GPIO number: the ESP32 pin labeled `8` is GPIO8, for example. Do not count to the eighth physical header pin.

### Why these connections are needed

- `3V3 → VCC` powers the sensor at a voltage compatible with ESP32 GPIO logic.
- `GND → GND` completes the power circuit and ensures both devices interpret signal voltages relative to the same reference. Any ESP32 pin clearly labeled `GND` may be used because the ground pins are connected internally.
- `GPIO8 → SDA` lets the ESP32 send register addresses and configuration values and lets the MPU6050 return sensor data on the same wire.
- `GPIO9 → SCL` lets the ESP32 clock each bit transferred on SDA.

GPIO8 and GPIO9 are a project choice, not fixed MPU6050 requirements. The ESP32-S3 GPIO matrix can route peripheral signals to multiple GPIO pins; the firmware must be configured to match the physical wiring.

```text
ESP32-S3 (I²C controller)       MPU6050 (I²C target)

3V3  --------------------------> VCC
GND  --------------------------> GND
8    -------- data both ways ---> SDA
9    -------- clock -----------> SCL
```

## Unused MPU6050 pins

- `AD0` selects the least-significant bit of the I²C address. On common breakout boards, leaving it disconnected normally selects `0x68`; driving it high selects `0x69`.
- `INT` is an optional interrupt output. A later version can use it to signal that a fresh sample is ready.
- `XDA` and `XCL` form the MPU6050's auxiliary I²C interface for external sensors. They are not needed for this demo.

Leave all four unused pins disconnected for the initial test.

## Breadboard checks before power

- Each MPU6050 header pin must occupy a different numbered breadboard row.
- Confirm `3V3` connects to `VCC`, never `GND`.
- Confirm `GND` connects to `GND`.
- Confirm GPIO8 connects to `SDA` and GPIO9 connects to `SCL`.
- Check for bent pins, loose jumpers, or exposed conductors touching one another.
- Do not connect the separate breadboard power-supply module for this test.

After checking the wiring, reconnect USB. This demo expects the MPU6050 at `0x68`; its reusable library also exposes `0x69` for a board whose AD0 pin is high.

## Run the demo

From the repository root and inside the Nix development shell, compile, flash, and monitor the demo:

```sh
cargo run --target xtensa-esp32s3-none-elf -Zbuild-std=core,alloc --release -p imu-demo
```

A correctly connected MPU6050 with AD0 low should produce output similar to:

```text
MPU6050 confirmed and awake
raw accel=[...] gyro=[...] temp=...
units accel(g) x=... y=... z=... | gyro(dps) x=... y=... z=... | temp=... C
```

Readings use an `IMU`-prefixed CSV protocol at approximately 50 samples per second. Each row contains time in milliseconds, acceleration in `g`, angular velocity in degrees per second, and temperature in degrees Celsius. Pressing `Ctrl+C` closes the monitor but leaves the firmware running on the ESP32.

While sampling is healthy, the onboard GPIO48 RGB LED uses the shared `onboard-rgb` library to breathe green. This provides a visible heartbeat even when no serial monitor is attached.

### Wi-Fi telemetry

Serial mode remains the default. To send the same `IMU,...` rows to UDP port `7778` on the Mac, enable the optional Wi-Fi feature with compile-time environment variables:

```sh
export WIFI_SSID='your-network-name'
export WIFI_PASSWORD='your-network-password'
export IMU_UDP_HOST="$(ipconfig getifaddr en0)"
ESPFLASH_PORT=/dev/cu.usbmodem1234561 \
  cargo run --target xtensa-esp32s3-none-elf -Zbuild-std=core,alloc --release -p imu-demo --features wifi
```

For a basic receiver, run `nc -u -l 7778` on the Mac. The shared `wifi-telemetry` library adds a newline to each UDP datagram and automatically reconnects the ESP32 after a Wi-Fi interruption. Credentials are not stored in Git, but they are embedded in the resulting firmware binary, so do not distribute that binary.

To feed the existing 3D orientation visualizer over Wi-Fi, stop `nc` and run:

```sh
nix run .#imu-visualizer -- --udp
```

## Library and tests

Sensor behavior is implemented in `src/lib.rs`, independently of the ESP32 executable. The library owns identity checking, wake-up and range configuration, register decoding, and conversion into `g`, degrees per second, and degrees Celsius. `src/main.rs` only creates the ESP32 I²C peripheral and displays the library's results.

Firmware startup is also fallible: `main` passes hardware ownership to `run`, then handles any returned setup error in a persistent safe-state loop. Expected setup failures do not use `unwrap()` or panic. The existing `esp-backtrace` panic handler remains a final boundary for programming defects and other unexpected failures.

To run the library unit tests on the Mac, use ordinary Cargo from the repository root:

```sh
cargo test --locked -p imu-demo --lib
```
